# OpenRumble 🐘

> 以非洲象「雙通道預警」為靈感的開源風險管控框架：整合 **Falco eBPF**、**auditd** 與 **Zeek**，把主機與網路的零散訊號關聯成可追溯的風險事件。

**狀態：🚧 規劃與設計階段。** 目前尚無可用程式碼，本文件描述的是專案的目標與設計方向，內容會隨開發調整。

---

## 為什麼叫 OpenRumble？

非洲象會用兩種管道傳遞危險訊息：

- **空氣中的次聲波**：低於人類聽力下限的低頻「隆隆聲」（rumble），可以傳到遠處。
- **地面的震動**：跺腳、奔跑與低頻叫聲會在地面產生震動，其他象可以透過腳底與象鼻感知。

此外，年長母象累積的經驗是整個象群應對天災與威脅的關鍵；研究顯示，這類經驗一旦「斷代」，族群的生存機率會受影響。

這三件事剛好對應到風險管控的三個痛點：

| 大象的行為 | 對應的偵測層 | 本專案的模組 |
|---|---|---|
| 腳底感知地面震動 | 主機核心層行為（syscall、程序、檔案） | `footfall`（Falco eBPF） |
| 低頻次聲波遠距傳遞 | 網路流量與連線行為 | `rumble`（Zeek） |
| 母象的記憶與經驗傳承 | 可稽核的紀錄、風險登記與事件教訓 | `matriarch`（auditd + 風險登記簿） |

## 核心設計理念

### 1. 雙軌部署，交叉驗證

主機側同時部署 **Falco（eBPF）** 與 **auditd**，兩者獨立觀察同一台主機：

- 兩邊都看到 → 高可信度事件。
- 只有一邊看到 → 標記為「需要查證」，可能是規則缺口、效能丟包，或偵測機制被繞過。

### 2. 主機與網路視角關聯

**Zeek** 提供網路側的連線、DNS、TLS 等中繼資料。OpenRumble 的目標是把主機事件與網路事件以時間、主機、程序、連線等欄位關聯起來，而不是各自產生獨立告警。

### 3. 從偵測走到風險管理

偵測事件不是終點。OpenRumble 希望把事件對應到：

- **風險登記簿**：事件屬於哪一項風險、風險擁有者是誰、處置進度如何。
- **控制項映射**：可對應 ISO/IEC 27001:2022 附錄 A（例如 A.8.15 日誌、A.8.16 監控活動）與 MITRE ATT&CK 技術。
- **經驗留存**：事件結案後的教訓寫回知識庫，避免人員異動造成知識斷代。

## 規劃中的架構

```text
   主機 ───────────────────────────────┐
   ├─ Falco (eBPF)  ──► footfall ──┐   │
   └─ auditd        ──► matriarch ─┤   │
                                   ├──► 事件正規化與關聯 ──► 風險評分 ──► 風險登記簿 / 告警
   網路                            │
   └─ Zeek          ──► rumble ────┘
```

| 模組 | 負責內容 | 資料來源 |
|---|---|---|
| `footfall` | 主機行為規則與事件正規化 | Falco（eBPF） |
| `rumble` | 網路偵測腳本與日誌正規化 | Zeek |
| `matriarch` | 稽核紀錄、風險登記簿、事件教訓知識庫 | auditd |
| `core` | 共同事件格式、關聯鍵、風險評分 | 以上三者 |

輸出端預計可串接既有的日誌平台（例如 Graylog / OpenSearch）。

## 預期的指令介面（草案）

以下僅為設計草案，指令名稱與參數尚未定案：

```bash
rumble scan                 # 檢查 Falco、auditd、Zeek 是否正常運作與覆蓋率
rumble footfall list        # 列出主機行為規則
rumble correlate --since 1h # 關聯近一小時的主機與網路事件
rumble risk list            # 檢視風險登記簿
```

## 適用情境

- 以 Linux 主機為主、需要主機與網路雙視角監控的環境。
- 需要把監控紀錄與風險管理、稽核證據連結起來的組織。
- 希望降低資深人員離職造成經驗流失的資安團隊。
